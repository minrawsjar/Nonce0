## What actually works on-chain

**Post-quantum signature verification: 1,491,721 gas** at `k=32, a=8` — about
**5% of an Arc 30M block**. Pure keccak, no precompile, nothing an elliptic
curve is doing. §5.5 said to measure rather than hand-wave; that is the measurement.

That number matters most next to the one beside it. The eight-member ring proof
(§6) measures at **1.08 MiB and ~9× a whole block** to verify — `node
backend/zk/bench.ts` reproduces it — so it cannot go on-chain at all. **Wallet
authorisation is quantum-safe on-chain today. Sender anonymity is not.** That
asymmetry is the honest shape of this protocol, and the contracts are built to
say so rather than hide it.

## The rule PQKeyRegistry exists to enforce

After registration, **only a valid signature under the account's current PQ key
can change that account's key.** There is deliberately no owner, no admin, no
pause, no upgrade hatch and no ECDSA guardian in the file. A quantum adversary
holding any such fallback would use it to rotate `pkCommitment` to a key it
controls, and every other line of this protocol would be decoration.
`msg.sender` authorises exactly one thing — the first registration, which
somebody has to pay for — and never a change to a registered key.

`test_noAddressCanChangeAKeyWithoutAPqSignature` is that claim as a test.

Registry actions are domain-separated from user payloads, so a signature
authorising a transfer can never be replayed as a rotation.

## Cross-language vectors, not inspection

`test/fixtures/*.json` are generated by `packages/pq-wallet` in TypeScript. The
Solidity verifier is checked against signatures it had no part in producing —
public key, leaf indices, `pkCommitment`, scheme id and full 9,251-byte
signatures. Two implementations that agree by reading agree by luck; these
agree by test.

Regenerate them if the TypeScript hashing changes. Both sides hash the same
length-prefixed encoding, and a separator that can occur inside a field is not
a separator — `"a:b" + "c"` and `"a" + "b:c"` hashing alike is a forgery, not a
style question.

## Why the pool takes two transactions

`SingleNotePqVerifier` publishes the note secret in calldata. A one-shot spend
would be trivially front-run: copy the secret out of the mempool, resubmit with
your own recipient and more gas. So the pool commits first —
`keccak(recipient, proof, salt)` — and reveals after `COMMIT_DELAY_BLOCKS`.
Someone who learns the secret at reveal time has no earlier commit of their own,
and making one costs a delay by which the nullifier is spent.
`test_frontRunningTheRevealFails` walks exactly that attack.

The flag lives on `ISpendVerifier`, not the pool: a ring proof binds its
recipient into its own Fiat-Shamir challenge and needs none of this.

## Two things the pool does not have

**No `mapping(address => uint256)`.** A deposit creates an opaque commitment; a
balance is only the set of notes you hold secrets for. If wallets moved their
own tokens the transfer's `from` would name the spender and pooled custody
would be pointless.

**No event linking a nullifier to a ring member.** `Spent` names the nullifier
and the recipient — both public at settlement per §3 — and never the commitment
it opened. An event tying those together would undo the ring from the indexing
side, which is §8's hard constraint.

## Nullifiers never bind the recipient

`noteNullifier(secret)` binds the secret and the pool and nothing else. A
recipient-dependent nullifier lets one note be spent once per recipient, without
limit — an unlimited mint. Spec §6.4 currently writes it the wrong way;
`test_changingTheRecipientDoesNotMintANewNullifier` pins the right one.

## Commitments differ by mode, on purpose

The ring circuit commits with AES-128 (cheap in AND gates, which is what an
MPC-in-the-head proof pays for). `SingleNotePqVerifier` commits with keccak
(the native opcode, which is what the EVM pays for). A pool is one mode or the
other and `capabilities()` reports which, so an interface can never render a
single-note spend as eight-member anonymity.

## Deploy

```sh
export PRIVATE_KEY=0x...
forge script script/Deploy.s.sol --rpc-url $ARC_RPC_URL --broadcast
```

`USDC` defaults to Arc's 6-decimal ERC-20 at `0x3600…0000`; `DENOMINATION`
defaults to 1 USDC. Arc's *native* USDC is 18 decimals and pays for gas — the
same asset through two interfaces, and confusing them is a factor of 10¹².

The verifier binds the pool id and the pool derives that id from its own
address, so the script constructs the verifier against a predicted address and
refuses to proceed if the prediction is wrong.
